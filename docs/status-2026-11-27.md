# Status, 2026-11-27

Written to be wrong in public. Every number here is one `revi` or `ls` away.

## Can we decompile it?

**Statically, yes. To source, barely. At runtime, not yet.**

The honest unit is 0: nothing has been executed against the real machine and
compared. `ported` means "a source body exists that compiles and passes a trap
record", which is a claim about my reading, not about the game.

What is genuinely finished is the *measurement*: we can map, scan, rank, draft
with kuna, compile under MSVC 19.52, drive bodies with stubs, corrupt an extent
to prove the gate, and diff a normalised run. That is a decompiler's
skeleton — no muscle on it yet.

## New facts, and what they change

1. **The package is 2.07 % done (4.65 GB), not "two days away".** Every file is
   preallocated to full size, so `du` shows 208 GiB while almost all of it is
   zero; only a verify pass tells the truth (`Have: 4.65 GB verified`). At
   590 KB/s the remaining 204 GB is ~4 days. Definition of done is now: **100 %
   verified and one clean re-verify with zero corrupt pieces.** Any ETA quoted
   from `Downloaded` bytes is fiction — the daemon logged 363 GB downloaded while
   holding 4.65 GB of it.
2. **Verify before a campaign, not after.** `Percent Done: 0.00 %` with data on
   disk was the signal; a verify showed 2 %. Also: the daemon sat `Idle` after
   verifying and needed `--start`. Cheap check in `tools/`, run before any run
   that depends on package bytes.
3. **41 GB free is the whole margin.** 96 % used. Zeros are preallocated, so the
   download will not grow much, but kuna temp, `decomp/` builds and the
   decompile-project exports all land on the same disk. `--max-fn-memory` and
   scratch under `/tmp` stay mandatory; the 209 GB of game data cannot move.
4. **Aster is a single point of failure and it failed today** (~20 min, tailnet
   session dropped mid-command, no LAN address). Nothing in the loop is
   redundant: bytes, wine, MSVC and the oracle all live there.
5. **kuna builds on macOS with stable 1.98.1/1.99.0.** Nightly is now *worse*
   than stable: current nightly removed `core::intrinsics::abort`, and the
   `branches` dependency calls it, so the workspace does not build on
   `nightly-2026-11-21`. Local build of the decompiler takes ~6 min. A second
   build/test host exists and costs one `rustup` pin.
6. **`kuna twins` exists** (PR #12): repeated bodies reported with address
   operands masked, grouped, never excised. Outlining no longer needs a human to
   read addresses first; the remaining work there is helper emission.

## kuna additions, ranked

1. **twins report** — done, PR #12.
2. **vftable recovery without RTTI** (#9): group `[this+0]` stores of one address
   across constructors, name the table by its address, symbolise slots, type the
   `this` parameter. Unblocks G2b and G5.
3. **`--seh-report`** (#3): list handler-bearing extents with the personality
   each resolves to, and print the decoded scope table in a comment when
   reconstruction declines. Today `sub_140001000` has unwind flags `0x1` and
   still prints flat — silently.
4. **`kuna datarefs`**: data slots holding code pointers with the reading
   function, the slot-level counterpart to `xrefs`' pointer rows.
5. **`--expect` / host verify**: decompile, then run the emitted C against
   `REVI_STUB_RET`-style stubs and compare. kuna has no notion of an executed
   body; we built one by hand in `reVI` and it is the only thing that separates
   `ported` from `matching`.
6. **No-PDB twin fixture**: four inline sites plus a control object of
   same-shaped unrelated bodies, `/Zi` stripped. Without it the twin threshold is
   unmeasured, which is why #6/#10 keep stalling on "not verified".

## Risks

- **Download stall or disk exhaustion** stops everything downstream; mitigate
  with the preflight and by keeping claims exe-only until 100 %.
- **Aster down** stops builds and the oracle; mitigate with the macOS toolchain
  and by committing everything (decomp/ included) so a second host can start.
- **Drafting defects** are the measured failure mode, not analysis mistakes;
  the audit gate must keep running on every PR or the 24 claims rot.
