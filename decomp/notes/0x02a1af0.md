# 0x02a1af0

156 bytes. Not the handler itself: the try-lock `0x00037a50` tail-calls
**0x2a1be0**, which is 0x10 bytes into this function. That block is a one
instruction stub:

```
0x2a1be0: jmp 0x569f5
```

So this function is a shared landing pad; the real handler lives at `0x569f5`
and begins by calling `WaitForSingleObject(0, 0xffffffff)`.

## Why it matters

This is the first place a *data* pointer (the `g_slots` table at 0x7921fc0)
reaches code, so it is the first handoff the exe-only harness can follow on its
own: `g_slots[0]` is relocated at load and the call lands here without any game
state.

## Evidence

`0x00037a50` with a zero word, `REVI_STUBS=1 REVI_GS=1`:

```
word before 0x00000000
word after  0x00000010 00000000   (slot 0 << 28 | 0x10000000)
stub WaitForSingleObject args 0 ffffffff from 0x56a0d
```

The reservation is confirmed by execution, which is the strongest evidence any
body has had so far.

## Open

* 0x569f5 is the actual handler; read it next, it is what the reservation buys.
* Entry is at +0xF0, so the first 0xF0 bytes are a separate function's tail.
  Merits a split in the map's model.
