# 0x01fa5270

28 bytes. Instruction-for-instruction equal to our build, displacements aside:
both are 28 bytes and the same opcodes. This is the first body where the
reading is not just plausible but reproduces the original.

Two more extents with the same body follow at 0x01fa5340 and 0x01fa5480; they
are `alias` rows and are retired by this one.

## Original

```
sub  rsp, 28h
mov  rax, [rip+0x8ab12c5]   ; 0xaa56540, a global holding an object pointer
lea  rcx, [rip+0x8ab12be]   ; 0xaa56540 again, the address of that global
call [rax+0x30]             ; sixth slot of the object's table
mov  al, 1
add  rsp, 28h
ret
```

Both displacements resolve to the same global: the object is loaded from it,
and the global's *address* is passed as the argument. The call is not a member
call through a pointer — it is a table slot read from the loaded object, which
is why the compiler keeps the pointer in `rax` and builds the argument
independently.

## Reading

```cpp
extern char* g;                      // 0xaa56540
bool f() { (*(void (**)(void*))(g + 0x30))(&g); return true; }
```

Equivalent member-call spellings (`g->v6(&g)` with a virtual at slot 6) emit an
extra `mov rcx,[g]` + `mov rax,[rcx]` pair and are 32 bytes; the raw table call
is the one that matches.

## Open

* What is `g`? 0xaa56540 is in `.data`; the slot is only read here. Follow the
  writers to name the class.
* Why pass the address of the pointer and not the object? Probably a
  registration callback that stores or compares it.
* Return is a constant `true`; find the caller to see whether it branches on it.
