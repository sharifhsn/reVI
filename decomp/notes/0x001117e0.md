# 0x001117e0

32 bytes, one chunk, leaf apart from one call. First real decompile: it proves
the loop, not anything about the game.

## Original

```
sub  rsp, 28h
cmp  cl, 16h
je   .false
mov  ecx, edx
call 0x4f76200
and  al, 0FEh
cmp  al, 4
sete al
add  rsp, 28h
ret
.false:
xor  eax, eax
jmp  .epilogue
```

Argument 1 arrives in `cl` (narrow, unsigned — the compare is 8-bit),
argument 2 in `edx` and is forwarded as the callee's first argument (`ecx`).
So: one `unsigned char` and one 32-bit argument.

## Reading

```
bool f(unsigned char a, int b) {
    if (a == 0x16)
        return false;
    return (g(b) & 0xfe) == 4;
}
```

`g` (0x4f76200) returns in `al`; `and 0xfe` clears bit 0 before comparing to 4,
so the result is true for `g` values 4 and 5. 0x16 looks like an enum case that
the callee does not accept.

## Evidence status

* `ported`: the C compiles and matches the reading above, locally.
* Not `matching`: no oracle run yet. The test vectors below are derived from

## Codegen note

MSVC 19.52.37029 (/O2 /GS-) emits 35 bytes against 32, and puts the shared
epilogue inline with a `jne`, where the original jumps forward to a cold
`xor eax,eax` and shares one epilogue. Four source shapes (`bool`, `_Bool`,
`int`, temp variable, `/Ox`, `/Ob3`) all gave the same 35/34-byte shape, so the
gap is probably the compiler version, not the source. Behaviour is identical;
byte equality is not claimed.
