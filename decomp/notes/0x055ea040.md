# 0x055ea040

30 bytes. Compares the argument to `__security_cookie`, rotates it, and tail
calls 0x5600570 otherwise. No return value: the scrambled value is left in
`rcx` and callers read that.

## Original

```
cmp  rcx, QWORD PTR [rip+0x11f7ff1]   ; 0x67e2038 = __security_cookie
jne  .tail
rol  rcx, 0x10
test cx, 0xffff
jne  .unrotate
ret
.unrotate:
ror  rcx, 0x10
.tail:
jmp  0x5600570
```

`0x67e2038` holds `0x00002B992DDFA232` — the default x64 `/GS` cookie, which is
why a first run with argument `0` took the slow path: after base relocation the
slot is not 0, and the cookie is not a zero sentinel.

## Reading

```c
void f(uintptr_t v) {
    if (v == __security_cookie) {
        v = rotl(v, 16);
        if ((v & 0xffff) == 0) return;   // rcx carries the rotated value
        v = rotr(v, 16);
    }
    sub_5600570(v);
}
```

`rol 16` moves the top 16 bits into the low half, so the test after the
rotation is on the *source's* bits 48..63. For the cookie (`0x00002B99…A232`)
those are zero, so the cookie always takes the return path.

## Evidence

Recorded with `revi call`:

| argument | rcx after |
|---|---|
| `0x2b992ddfa232` (the cookie) | `0x2b992ddfa2320000` = `rotl16(cookie)` |
| anything else | unchanged, after the tail call |

That is the whole transform, confirmed by execution rather than by reading.

## Codegen

22%, 9 instructions against 8. The core is identical (`cmp` against the cookie
slot, `rol rcx`, the low-half test) but MSVC inverts the branch and re-materialises
the tail argument instead of keeping it in `rcx`, costing a `jmp` and a `mov`.
Three shapes tried and the rotation-back is needed for correctness, so the
remaining gap is placement, not semantics.

## Open

* 0x5600570 is the slow path for the same argument — read it next, they belong
  together.
* Where is a cookie value used as a *data* sentinel? Check the callers; this may
  be pointer obfuscation, not stack protection.
