# 0x056006b4

113 bytes. Manual stack walker: captures the context, then unwinds two frames
with `RtlVirtualUnwind`, returning handler and establisher for each. Called by
the cookie initialiser `0x05600570` with `&g_1808af0`.

## Original shape

```
push rbx/rsi/rdi ; sub rsp,0x40
rbx = rcx                       the CONTEXT
call RtlCaptureContext(rcx)     rcx still holds the CONTEXT
rsi = [rbx+0xF8]                CONTEXT.Rip
edi = 0
.loop:
r8d = 0 ; rdx = &image_base ; rcx = rsi
rax = RtlLookupFunctionEntry(pc, &image_base, 0)
if (!rax) break
... RtlVirtualUnwind(0, image_base, pc, entry, ctx, &handler, &establisher, 0)
edi++ ; if (edi < 2) goto .loop
```

Imports resolved by slot: `RtlCaptureContext` (0x6793EC8),
`RtlLookupFunctionEntry` (0x6793ED0), `RtlVirtualUnwind` (0x6793ED8), all from
`api-ms-win-core-rtlsupport-l1-1-0.dll`. `CONTEXT.Rip` at `+0xF8` is what makes
the purpose identifiable.

## Evidence

Runs under `REVI_STUBS=1` without faulting: the stubbed `RtlCaptureContext`
leaves the context zero, `CONTEXT.Rip` is 0, and the stubbed
`RtlLookupFunctionEntry` returns 0, so the loop exits on the first test. That
confirms the call sequence and the exit on a null entry; the unwind itself needs
the real APIs.

## Open

* Why two frames? Either the caller is a trampoline, or this records the two
  frames a fault needs.
* Handler and establisher are written to stack slots and not used here; the
  caller's second call (`0x05600728`) is what consumes the context.
